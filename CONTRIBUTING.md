# Contributing

Discuss substantial changes in an issue before implementation. Keep pull requests focused, describe behavior and security or data implications, and include the checks actually performed. Do not include secrets, customer data, database dumps, or backups.

Follow [AGENTS.md](AGENTS.md), [first-run setup](docs/FIRST_RUN.md) and [frontend guidance](docs/FRONTEND.md). The project uses Static Verification First: no dedicated tests, fixtures, frameworks, or runtime checks without explicit user authorization. Do not start applications, databases or services to verify changes. Use existing Ruff/AST/offline migration checks (`uv run python scripts/check.py`), TypeScript (`npm run check --prefix frontend`) and source publication checks (`uv run python scripts/check_delivery.py`). These commands do not build or connect to a database. Dependency setup uses `uv sync --locked` and `npm ci --prefix frontend`.

Backend routes live in `src/support_agent/api`, business operations in `services`, database models in `models.py`, and additive schema changes in `migrations/versions`. React features, adapters and shared components live under `frontend/src`; static Demo and API adapters must remain isolated. Keep authorization in server services and reuse existing transactional boundaries. Use Ruff checks/formatting and TypeScript `tsc --noEmit`; do not restore removed automated test suites. Make targeted dependency updates with their lockfiles and license review, not unrelated framework upgrades.

CI performs source-only static verification on Python 3.13 / Node 22; it does not start PostgreSQL, migrate data, build packages or run tests. Supported runtime versions in project metadata are compatibility targets, not a verified runtime matrix. The manual Pages workflow is a separate, explicitly authorized publishing path. Report results as PASS, FAIL, NOT_RUN, NOT_AVAILABLE, NEEDS_RUNTIME_VERIFICATION or FALSE_POSITIVE. See [release review](docs/RELEASE_ACCEPTANCE.md) and [SECURITY.md](SECURITY.md).
